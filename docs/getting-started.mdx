## Requirements

- Node.js 22 or newer
- A repeatable integration scenario

<Steps>

<Step>

### Install

Install GrantTrace `0.1.0-beta.1` from a package archive built from source.
Run these commands from the project where you want to use GrantTrace:

```bash title="Terminal"
granttrace_checkout="$(mktemp -d)/GrantTrace"
git clone https://github.com/ToxFied/GrantTrace.git "$granttrace_checkout"
corepack enable
pnpm --dir "$granttrace_checkout" install --frozen-lockfile
npm --prefix "$granttrace_checkout" pack \
  --pack-destination "$granttrace_checkout"
pnpm add --save-dev \
  "$granttrace_checkout/granttrace-0.1.0-beta.1.tgz"
```

This source-packaging step is temporary. Once the beta is published, installation
becomes:

```bash title="Terminal"
pnpm add --save-dev granttrace@beta
```

<Callout title="Developing GrantTrace">
  When working on GrantTrace itself, substitute `pnpm granttrace` for `pnpm exec
  granttrace`.
</Callout>

</Step>

<Step>

### Record a scenario

```bash title="Terminal"
pnpm exec granttrace record issue-triage -- \
  pnpm test -- issue-triage
```

No source edit or separate initialization is required for the standard Node.js
path. GrantTrace injects a preload into the child process and observes supported
GitHub REST calls through Node's global `fetch`. Standard Octokit clients use
that path automatically. Automatic capture is restricted to requests targeting
exactly `https://api.github.com`; off-origin responses are ignored even if they
include a permission-like header.

The command after `--` is passed as an argument array without a shell. Output
streams to your terminal. Recording the same scenario name again atomically
replaces its previous local observation file. On the first recording,
GrantTrace creates private `.granttrace/` state and adds it to `.gitignore`
before the test process can start.

`granttrace init` remains available when you want to prepare the project
explicitly. `granttrace doctor` is optional diagnostics, not an onboarding
step.

</Step>

<Step>

### Review the diff

The same `record` command prints the permission, route, evidence, and
attribution diff. In an interactive terminal it asks whether to accept that
exact change. The default answer is no; acceptance always requires a person.

In CI or another noninteractive terminal, GrantTrace never prompts or accepts.
A changed contract exits `6`. Review it locally, or use
`granttrace check` followed by `granttrace check --accept` when you want the
review and acceptance as separate commands.

Commit `granttrace.lock.json`. Keep `.granttrace/` local and ignored. That is
the full normal onboarding flow:

```text
install → record → review → commit
```

</Step>

</Steps>

## Add more scenarios

```bash
pnpm exec granttrace record release-read -- \
  pnpm test -- release-read
pnpm exec granttrace scenario list
```

Each successful recording solves one aggregate contract while preserving which
scenario exercised each route.

Removing the final recording is also a reviewable contraction. After
`check --accept`, the v2 contract has zero observed scenarios, routes, selected
permissions, and unknowns. Validated manual keeps are retained until you remove
them explicitly; zero observed coverage never turns a keep into proven
necessity.
