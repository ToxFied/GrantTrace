Don't know what the fuck you're doing? You're in the right place. GrantTrace
does one job: **it watches your app talk to GitHub and writes down the
permissions it actually used.** Give it one command. It gives you a receipt.

## Before you start

- Node.js 22 or newer
- a Node.js project with a `package.json` file
- one test or script that makes your app perform a real GitHub action

No test command yet? Stop here. GrantTrace watches behavior. It does not invent
it. Give your app a repeatable test or script first, then come back.

<Steps>

<Step>

### Find the right folder

Open a terminal in your app's folder. If you can see `package.json`, you're
probably home.

</Step>

<Step>

### Install GrantTrace

```bash title="Terminal"
npm install --save-dev granttrace@beta
```

If your project uses pnpm:

```bash title="Terminal"
pnpm add --save-dev granttrace@beta
```

</Step>

<Step>

### Record one real scenario

```bash title="Terminal"
npx granttrace record issue-triage -- npm test -- issue-triage
```

That command has three useful pieces:

- `issue-triage` is a short name you make up for the behavior being tested.
- The `--` is the fence. GrantTrace is on the left.
- Your normal test command is on the right. Replace
  `npm test -- issue-triage` with yours.

GrantTrace runs the command, watches its GitHub REST requests, and prints what
it saw. For pnpm projects, use `pnpm exec granttrace` and your normal pnpm test
command instead.

Here is the same flow in a real terminal. The screenshots are generated from
the repository's hermetic fixture, so they contain no credentials or live
GitHub data.

<img className="w-full rounded-xl border border-fd-border" src="/cli/01-record.png" alt="Terminal showing GrantTrace recording the issue-triage scenario" />

</Step>

<Step>

### Review and keep the receipt

The same command prints the permission, route, evidence, and attribution diff,
then asks whether you want to accept that exact change. Read it. If it matches
the behavior you just ran, type **y**. The default answer is no. This is the one
bit you should not autopilot.

GrantTrace creates `granttrace.lock.json`. Commit it. That file is the useful
bit: a reviewable record of the permissions this behavior used. The private
scratch files in `.granttrace/` stay local; GrantTrace adds that directory to
`.gitignore` for you.

That's the full normal onboarding flow:

```text
install → record → review → commit
```

The review and acceptance steps are separate, visible decisions:

</Step>

</Steps>

<details className="my-8 border-y border-fd-border py-4">
  <summary className="cursor-pointer font-medium">How recording works</summary>
  <div className="mt-4">
    <p>
      No source edit or separate initialization is required for the standard
      Node.js path. GrantTrace injects a preload into the child process and
      observes supported GitHub REST calls through Node's global <code>fetch</code>.
      Standard Octokit clients use that path automatically.
    </p>
    <p>
      Automatic capture is restricted to requests targeting exactly
      <code>https://api.github.com</code>. Off-origin responses are ignored even
      if they include a permission-like header. The command after <code>--</code>
      is passed as an argument array without a shell, and output streams to your
      terminal.
    </p>
    <p>
      Recording the same scenario name again atomically replaces its previous
      local observation file. On the first recording, GrantTrace creates private
      <code>.granttrace/</code> state before the test process can start.
      <code>granttrace init</code> remains available for explicit setup, while
      <code>granttrace doctor</code> is optional diagnostics.
    </p>
    <p>
      In CI or another noninteractive terminal, GrantTrace never prompts or
      accepts. A changed contract exits <code>6</code>. Review it locally, or use
      <code>granttrace check</code> followed by
      <code>granttrace check --accept</code> when you want review and acceptance
      as separate commands.
    </p>
  </div>
</details>

## Add more scenarios

```bash
npx granttrace record release-read -- \
  npm test -- release-read
npx granttrace scenario list
```

Each successful recording solves one aggregate contract while preserving which
scenario exercised each route.

Removing the final recording is also a reviewable contraction. After
`check --accept`, the v3 contract has zero observed scenarios, routes, selected
permissions, and unknowns. Validated manual keeps are retained until you remove
them explicitly; zero observed coverage never turns a keep into proven
necessity.

## One honest limit

GrantTrace only knows what your command touched. Untested paths are still
untested. No magic. No bullshit.
